## 1. 最终目标

最终 Agent 必须做到：

**只观察当前 4×4 棋盘，通过一次神经网络前向计算，直接决定上、下、左、右。**

正式运行时不使用：

- Expectimax
- rollout
- 多步搜索
- N-tuple 辅助决策
- Teacher
- Replay Buffer
- 高位残局池

最终流程：

当前棋盘  
→ 神经网络  
→ 四个动作 Q 值  
→ 屏蔽非法动作  
→ 选择最高 Q 的合法动作

训练阶段则允许使用昂贵方法：

- 强 N-tuple Teacher
- 深 Expectimax
- 大规模 Self-play
- Search Correction
- 高位残局专项训练
- 精确计算随机出生期望

整个项目的核心是：

**把训练期间昂贵的搜索和经验，压缩进最终一次 NN forward。**

主目标固定为：

**最大化一局 2048 的平均最终游戏分数。**

不额外人为增加：

- 16384 奖励
- 32768 奖励
- 65536 奖励

之类的特殊奖励。

Champion 的主选择标准同样固定为：

**平均最终游戏分数。**

第一版使用：

`uint8[16]`

保存 16 个格子的指数。

不直接采用传统每格 4 bit 的实现。

因为 4 bit 只能表示：

0～15

65536、131072 以及更高边界情况。

# 6. 游戏环境必须先保证正确

正式训练前必须测试：

- 上下左右移动
- 合并顺序
- 一个 tile 一步不能连续合并两次
- merge reward
- 非法动作不能改变棋盘
- 非法动作不能生成新 tile
- 合法动作以后才 spawn
- terminal 判断
- legal mask
- 2 / 4 生成概率
- D4 旋转与镜像
- 65536+ tile

还必须进行随机自动测试。

例如：

移动完成但还没有 spawn：

tile 数值总和必须不变。

spawn 后：

总和只能增加 2 或 4。

环境存在未解决的规则错误时：

**禁止正式训练。**

# 7. 一次决策的正式定义

统一定义：

当前正式棋盘：

`s`

执行动作：

`a`

得到即时 merge reward：

`r`

形成还未出生随机 tile 的棋盘：

`x`

即 Afterstate。

然后随机出生 2 / 4：

得到下一正式棋盘：

`s'`

即：

`s → a → x → spawn → s'`

---

# 8. 网络保留三个 Head

网络保留：

- Q Head
- Value Head
- Afterstate Value Head

必须区分：

**三个 Head 的含义固定。**

但：

**三个 Head 的最佳训练方式需要实验。**

---

# 9. Q Head 的固定含义

Q Head 输出：

- Q(up)
- Q(down)
- Q(left)
- Q(right)

Q(s,a) 表示：

**在当前棋盘执行动作 a，并且之后按照当前目标策略继续玩，预计从现在开始总共还能获得多少游戏分数。**

其中包括：

当前动作立即获得的 merge reward。

---

# 10. Value Head 的固定含义

Value：

`V(s)`

表示：

**从当前正式棋盘开始，如果以后都按照当前 greedy 策略正常玩，预计还可以获得多少游戏分数。**

greedy 策略就是：

每一步选择当前 Q 最大的合法动作。

---

# 11. Afterstate Value Head 的固定含义

Afterstate Value：

`A(x)`

表示：

**当前动作已经移动合并完成，但随机 2 / 4 还没出生时，这个局面平均还有多少未来收益。**

它需要把所有可能的随机出生结果考虑进去。

---

# 12. 三个值的目标关系固定

目标含义满足：

`Q = 当前动作即时得分 + Afterstate 的未来价值`

Afterstate 的价值：

等于不同随机出生结果的未来价值按真实概率求平均。

当前棋盘 Value：

等于当前所有合法动作中最好的 Q。

因此：

三个 Head 描述的是同一套游戏价值。

---

# 13. “关系固定”不等于三个输出硬绑死

训练过程中：

Q、V、A 都只是神经网络预测。

不要求每个时刻严格满足：

`Q = r + A`

或者：

`V = max Q`

例如网络训练中可能暂时预测：

Q(left) = 100000

reward = 512

A(x) = 98000

它们暂时对不上完全正常。

训练目标会逐渐把它们拉向正确关系。

所以：

**固定的是三个值分别代表什么。**

不是把三个 Head 强制写成同一个公式输出。

---

# 14. Transformer 必须具有位置编码

Transformer 不能只知道：

“这里有一个 8192。”

它还必须知道：

“这个 8192 在棋盘哪里。”

因此 Transformer baseline 固定使用：

**Tile Embedding + Learned Position Embedding**

16 个棋盘格分别对应：

16 个可学习的位置向量。

每个 token 的输入：

`TileEmbedding(tile_i) + PositionEmbedding(i)`

第一版直接使用：

**16 个 learned absolute position embeddings。**

这不是实验项。

它属于 Transformer baseline 必需组成。

以后才可以实验：

- row / column embedding
- 2D relative position
- 其他位置表示

Residual MLP 因为 16 个格子按固定顺序展开，本身已经隐含位置，因此不需要同样的位置编码机制。

---

# 15. Afterstate Head 第一版输入方式

第一版：

Afterstate 本身作为一个完整 4×4 棋盘，

重新输入同一个网络主干。

然后：

Afterstate Head 输出一个 A(x)。

因此：

正式 state  
→ 主干网络  
→ Q + Value

Afterstate  
→ 同一个主干网络  
→ Afterstate Value

这种方法计算量稍高，

但是数学含义清楚、容易验证。

后续可以实验更快的实现。

---

# 16. 随机 Spawn 的真实规则

假设 Afterstate 有 n 个空格。

那么下一正式 state 一共最多：

`2n`

种。

因为每个空格分别可能出生：

2

或者：

4。

真实概率：

- 空格位置均匀随机
- 2：90%
- 4：10%

因此最多只有：

32 种下一 state。

---

# 17. 精确 Spawn Expectation

对于需要精确 target 的 Afterstate：

枚举所有可能的下一 state：

`s'_1 ... s'_k`

根据真实 spawn 概率：

`p_1 ... p_k`

然后求概率平均。

---

# 18. 不是每一步都精确枚举

大规模 Self-play 时：

不要求每一步展开所有随机出生情况。

普通游戏：

按照真实规则随机 spawn 一次。

另外抽取一部分状态：

计算精确 expectation。

这样避免训练速度因为大量额外 NN forward 急剧下降。

---

# 19. 精确 Spawn 优先用于

优先：

- Teacher 数据
- 8192+
- 16384+
- 32768+
- Search Correction
- 高价值状态
- NN 判断比较纠结的状态
- Afterstate 预测误差较大的状态
- 随机抽取的一部分普通状态

**棋力与计算成本最划算的比例。**

## 31.2 1-ply tuple checkpoint 如何用于 Expectimax

`greedy_1ply` 不是 M3 Search 深度上限。

该 checkpoint 原生给出：

```text
afterstate value:
V_tuple(x)
```

在正式 state `s` 上构造固定的 formal-state leaf adapter：

```text
L_tuple(s)
=
max over legal a [
    immediate_reward(s,a)
    +
    V_tuple(afterstate(s,a))
]
```

然后 M3 的 3-decision-depth Expectimax：

```text
root formal state
→ player
→ chance
→ player
→ chance
→ player
→ chance
→ formal-state leaf
→ L_tuple(s_leaf)
```

所以：

```text
1-ply tuple evaluator
可以作为多层 Expectimax 的 leaf heuristic
```

Search 的 `decision_depth` 仍只计算显式 Search 中的玩家决策次数。

leaf adapter 内部的 1-ply greedy evaluation：

```text
不额外修改 decision_depth
```

但必须在 metadata 中明确写：

```text
leaf_evaluator = tuple_afterstate_greedy_1ply_adapter
```

禁止把它误称为 neural `V(s)`。

## 31.3 tuple raw value 仍必须先校准

尽管 afterstate TD(0) 的 reward 单位与游戏分数一致，

M3 仍不得未经验证就把：

```text
V_tuple(afterstate)
```

或：

```text
L_tuple(formal_state)
```

直接视为精确 `FUTURE_SCORE`。

M3 必须完成 value-semantics / calibration probe。

在此之前固定分类：

```text
V_tuple(x):
RAW_TUPLE_HEURISTIC

L_tuple(s):
FORMAL_STATE_TUPLE_HEURISTIC

Expectimax root action value:
SEARCH_VALUE_RAW_LEAF
```

只有校准或原始算法定义证据足够时，
才允许升级为：

```text
FUTURE_SCORE
或
CALIBRATED_FUTURE_SCORE
```

M3 calibration continuation policy 固定为 frozen tuple checkpoint 的原生 `greedy_1ply`，用于验证/拟合 `V_tuple(x)` 与 `L_tuple(s)` 到真实 future score 的关系。该 calibration 不等于 repeated depth-3 Expectimax on-policy evaluation。

因此，单凭上述 greedy_1ply calibration，无论相关性多高，都不得把 `Expectimax root action value` 从 `SEARCH_VALUE_RAW_LEAF` 自动升级为 `FUTURE_SCORE` / `CALIBRATED_FUTURE_SCORE`。Search value 若未来需要绝对 future-score 语义，必须另有数学定义证据或专门的、明确预算的 repeated-Search on-policy gate；M3 默认不要求后者。

**M3 冻结 calibration 限制（M4+ 长期生效）：** calibration 共 128 states / 16 games，但固定 game-level split 后 validation 只有 **1 game / 8 states**，test 为 3 games / 24 states。虽然 `L_tuple` 与 greedy_1ply realized future score 的全局 Pearson / Spearman 很高，但 affine mapping 的 validation R² 与 test R² 差异很大，说明当前 holdout 太小，不能把该 affine mapping 当作可靠绝对标尺。M3 的最终决定固定为：**拒绝 calibration promotion，继续保持 `RAW_TUPLE_HEURISTIC` / `FORMAL_STATE_TUPLE_HEURISTIC` / `SEARCH_VALUE_RAW_LEAF`。** 后续 M4+ 不得复用 M3 affine 参数作为 absolute Q/V/A target；只有新的、样本量充分且独立验证稳定的 calibration gate 才允许重新审议。

- 哪个动作比哪个动作好

# 39. Teacher Value 校准

如果希望使用 Teacher 的绝对 action value 回归：

必须先验证或校准 Teacher evaluator。

校准目标：

让 Teacher evaluator 的输出对应：

**真实 future game score。**

可以使用大量完整轨迹。

对当前 M3 frozen tuple checkpoint，校准轨迹的 continuation policy 固定为其原生 `greedy_1ply`；记录某个 formal state 之后在该 policy 下真实获得的 future score，然后检查 / 拟合 `V_tuple / L_tuple` 输出和真实 future score 的映射关系。

不得把这里的“完整轨迹”解释成每一步 repeated depth-3 Expectimax 到 terminal。depth-3 Search action value 默认仍是 `SEARCH_VALUE_RAW_LEAF`，不能借 tuple calibration 自动获得 absolute future-score 语义。

只有某一组 Teacher target 自身完成对应语义验证/校准以后，才允许把**那一组** absolute value 用于 Student Q / V / A 的数值回归。`V_tuple / L_tuple` 的 greedy_1ply calibration 不自动赋予 depth-3 Search action value 相同语义；Search value 仍为 `SEARCH_VALUE_RAW_LEAF` 时只能用于 policy/ranking supervision。

# 51. 第一版 Double-Q 下一状态计算

`s'`

`G_T(s') = Q_T(s', a*)`

`G_T(s') = 0`

`s'`

也就是说：

`p_1 ... p_k`

`y_A = Σ p_i × G_T(s'_i)`

这就是：

该 Afterstate 的精确随机期望 target。

使用相同 Validation seed 集合分别测试：

Learner

Champion。

`Learner score - Champion score`

平均分提升范围。

说明暂时不能确认谁更强。

保持原 Champion，

# 性能工程总规范（M1～M12 均受约束）

本项目不仅要求算法正确，还要求在目标硬件上充分利用计算资源。

**“能够运行”不等于“性能合格”。**

任何实现如果虽然数学语义正确，但由于低效数据路径、过多 Python 调用、过小 batch、频繁 CPU↔GPU 同步、低效环境推进等原因，只达到合理实现吞吐的一小部分，则不得因为功能正确而视为阶段完成。

性能优化必须建立在 correctness 之上。

---

## P1. M0 Reference Environment 永久冻结

M0 的 `Reference2048Env` 永久作为：

**Golden Reference / Correctness Oracle。**

后续任何：

- FastEnv
- Vectorized Env
- LUT
- bit packing
- C++
- SIMD
- 多线程实现
- CUDA 实现
- Search move generator

都不得替换或修改 M0 reference 的规则语义。

高速实现必须与 M0 进行 differential test。

至少随机生成大量棋盘，并针对全部四个动作比较：

- afterstate
- merge reward
- moved / legal
- legal mask
- terminal
- 高 tile 行为
- D4 对称
- random spawn 支持集
- exact spawn enumeration 的 outcome 与 probability

在上述差分项上，规则结果必须满足下面 **P1-A** 定义的正式一致性规则。

任何性能优化只要造成超出 P1-A 允许范围的语义差异：

**直接判定失败。**

M1 发现 FastEnv 与 M0 不一致时，默认首先认为 FastEnv 有 bug。

除非能够给出最小可复现案例并证明 M0 本身违反冻结规格，否则禁止修改 M0 来适配高速实现。

---

## P1-A. M1 与 M0 的正式一致性规则（int64 representation exception）

本节是 M1 与 M0 一致性判定的**唯一正式条款**。

之前“FastEnv 必须与 M0 在任何情况下 100% 数值一致、任何 divergence 都直接失败”的绝对措辞，

因为已经过审计的 M1 存在一个**明确、刻意、已测试的 representation divergence**，

自本节起修正为下述精确规则。

### P1-A.1 必须 exact equality 的部分

在 M1 的正式可表示域内：

- movement
- afterstate
- moved
- legal
- terminal
- spawn
- D4
- 普通 reward

必须与 M0：

**exact equality。**

M1 的正式可表示域指：

```text
(N, 16) uint8 C-contiguous tile exponent batch
```

即所有 tile exponent 都能由 `uint8` 表示的范围。

### P1-A.2 唯一允许的 representation divergence

唯一允许的 representation divergence 是：

```text
M0 reward 使用任意精度 Python int。

M1 高速路径为了固定批量 dtype，
reward / score 使用 np.int64。
```

这是 representation 层面的差异，

**不是 value semantics 层面的差异。**

它不构成 M1 correctness failure，也不得被当作“M0/M1 语义不一致”。

### P1-A.3 溢出时的强制行为

如果真实：

```text
single-action reward
```

或：

```text
running score + reward
```

无法精确表示为：

```text
0 .. INT64_MAX
```

则 M1 必须：

```python
raise OverflowError
```

禁止：

```text
silent wrap
负数回绕
截断
dtype=object 绕过
逐 board Python int
```

即：

**M1 禁止 silent overflow。**

宁可显式报错，也不允许返回一个错误的数值。

### P1-A.4 reward representation 与 movement legality 必须区分

```text
reward 超出 np.int64
```

**不得改变**：

```text
legal_mask
terminal
movement legality
```

只要 tile exponent 本身仍可由：

```text
uint8
```

表示，

legal / terminal 必须继续与 M0 一致。

例如：

```text
[61,61,61,61]
```

LEFT 的真实 reward：

```text
2**63
```

M1：

```text
move_batch LEFT
→ OverflowError
```

但是：

```text
legal_mask_batch
is_terminal_batch
```

在同一个棋盘上仍必须正常计算，并继续与 M0 一致。

也就是说：

**reward 不可表示不等于局面不可表示。**

这两件事在实现与测试中必须严格分开。

### P1-A.5 tile representation overflow 仍属于 movement correctness

另外必须写清：

```text
255 + 255 -> exponent 256
```

已经超出：

```text
uint8
```

这**不是** reward representation divergence。

这是：

```text
tile representation overflow
```

M0 和 M1 都必须：

```python
OverflowError
```

因此：

reward-independent legal path

也不能允许：

```text
255+255 silent wrap
```

tile exponent 本身溢出属于 movement correctness，

必须与 M0 保持一致，不得用 P1-A.2 的例外来豁免。

### P1-A.6 该 divergence 与现实游戏范围的关系

必须说明：

该 divergence：

```text
不会影响正常真实 2048 训练路径
```

其原因是：

触发这些 reward 上限的 synthetic board：

远远超过真实可达对局范围。

但是：

仍然必须测试和显式处理，

因为：

环境代码禁止 silent overflow。

不要删除这些边界测试。

它们属于：

**长期 CI frozen regression suite 的一部分。**（见“持续集成 / GitHub Actions”章节）

## P4. 禁止逐棋盘 Python → GPU 推理

允许的基本形式：

大量棋盘

↓

连续内存中的 batch

↓

一次或少量批量 tensor transfer

↓

GPU batch forward

↓

一次得到大量动作

↓

批量推进环境

严格禁止主训练路径出现：

```python
for env in envs:
    q = model(env.board)
```

或者其他等价的：

**每个棋盘触发一次独立 GPU forward / CPU→GPU transfer。**

这种实现即使功能正确：

也不能通过性能验收。

## P5. FastEnv 数据布局必须面向批量吞吐

- 批量 action

- 每个环境保存大量 Python object

- 每一步创建大量临时小对象
- 每环境独立进行 Python function call
- 不必要的数据复制和 dtype 转换

实际布局由 benchmark 决定。

必要时比较：

- Array-of-Structures
- Structure-of-Arrays

最终以端到端吞吐为准。
